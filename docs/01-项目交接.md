## 1. 这个项目是什么

**课题**：基于 ESP32-CAM 与 STM32 的智能蚕房监测管控系统（箱体约 50×55×30 cm）

**双板分工**——这是整个设计的核心，答辩时要讲清楚：

```
┌─────────────────────────────────────────────────────────┐
│ PC（RTX 4060）                                          │
│   YOLO11 推理：蚕的数量 / 病蚕 / 异动                    │
│        │ POST /ai                                       │
│        ▼                                                │
│ ┌─────────────────────────────────────────────────────┐ │
│ │ ESP32-P4  —— 感知与决策层                            │ │
│ │   OV5647 1080p → ISP → JPEG                          │ │
│ │     ├─ /stream 网页推流（12.5MB/s 网口，用 1.3MB/s） │ │
│ │     ├─ SD 录像 MJPEG AVI（分段 + 空间水位）          │ │
│ │     └─ CSV 双流日志（遥测 + 事件，同一文件）         │ │
│ │   AI 规则引擎 → 下发执行器命令                        │ │
│ │        │ UART2 115200 JSON                           │ │
│ │        ▼                                             │ │
│ │ ┌─────────────────────────────────────────────────┐ │ │
│ │ │ STM32F103C8T6 —— 实时闭环层（保底层）            │ │ │
│ │ │   SHT30×2 采集 → 温湿度 PID → TEC/PTC/雾化/风扇  │ │ │
│ │ │   上电即独立工作，不依赖 P4                          │ │ │
│ │ └─────────────────────────────────────────────────┘ │ │
│ └─────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────┘
```

**分级控制的三个原则**（论文里可以单独一节）：

1. **保底层在 STM32**：P4 死机、网线拔了、PC 关机，蚕房照样维持温湿度 —— 这是"能用的系统"和"demo"的区别。
2. **决策层在 P4**：AI 只输出"看到了什么"，"该做什么"由 P4 的规则引擎决定，PC 不直接控制执行器。
3. **感知层在 PC**：YOLO11 在 4060 上跑，P4 不承担推理（算力和内存都不该浪费在这）。

## 3. 数据流：一份 JPEG，三个消费者

这是本系统最关键的一处设计，写论文时值得展开：

```
OV5647 ──MIPI-CSI 2lane──▶ ISP ──▶ RGB565 ──┬──▶ JPEG 编码（硬件/软件）
                                            │        │
                                    （软件测光用）    ▼
                                            │   s_out_buf[0/1] 双缓冲
                                            │   s_out_pub / s_frame_seq
                                            │        │
                        ┌───────────────────┼────────┴──────────┐
                        ▼                   ▼                   ▼
                 /stream 推流          录像线程              （AI 采帧）
             20ms 轮询 + seq 去重    83ms 轮询 + seq 去重
                 → 10 帧/秒            → 10 帧/秒
                        └────────── 同一批帧，逐帧一一对应 ──────────┘
```

**为什么只编码一次**：单颗传感器，做不出两路画面；编码两次 P4 也扛不住。所以推流和录像读同一份 JPEG 比特流 —— 网页看到的就是卡上存的。

**轮询必须快于帧周期**，否则相位漂移会漏帧：
- 相机 10 fps → 帧周期 100 ms
- 推流轮询 20 ms、录像轮询 83 ms → 两者都保证每一帧被取到一次
- 靠 `s_frame_seq` 去重，不会重复写同一帧

## 5. 引脚（P4 侧）

### 摄像头（MIPI-CSI）
| 信号 | GPIO |
|---|---|
| SCCB SDA | 7 |
| SCCB SCL | 8 |
| MIPI 数据 | 2 lane（FPC 排线） |
| PHY 供电 | **片内 LDO 通道 3 = 2.5 V** |
| 模组晶振 | 25.000 MHz（`0x3036` 除数即 25000000，无偏差） |

### MicroSD（SDMMC 4 线）
| 信号 | GPIO |
|---|---|
| CLK | 43 |
| CMD | 44 |
| D0 / D1 / D2 / D3 | 39 / 40 / 41 / 42 |
| 供电 | **片内 LDO 通道 4**（漏了这条就 0x107） |
| 卡检测 | **无 CD 脚** —— 换卡必须重启 |

### 以太网（IP101GRI，RMII 10/100M）
| 信号 | GPIO |
|---|---|
| TX_EN | 49 |
| TXD0 / TXD1 | 34 / 35 |
| CRS_DV | 28 |
| RXD0 / RXD1 | 29 / 30 |
| MDC / MDIO | 31 / 52 |
| PHY_RST | 51 |
| REF_CLK | 50 |
| PHY 地址 | 1 |
| MAC | e8:f6:0a:e8:cc:28 |

### 与 STM32 的 UART2
| P4 | 方向 | STM32 |
|---|---|---|
| GPIO22 (TX) | → | PA3（第 13 脚，USART2_RX） |
| GPIO21 (RX) | ← | PA2（第 12 脚，USART2_TX） |
| GND（右列第 7 行） | — | GND |

> ⚠️ **GPIO37/38 是 console UART**，不能挪作他用。
> ⚠️ 接板前先量两块板 GND 间电位差，**< 0.1 V 才接线**。

完整接线（含电源、继电器、MOS 管、TEC/PTC）见 [接线总表.md](接线总表.md)。

### ❌ 已知缺陷（按严重度）

1. **AI 决策的 `light_level` 语义不匹配** —— P4 发 `50/100/128`（当成百分比），STM32 侧是
   **0~4 档（每扇区点亮几颗）**，`Actuator_SetLightLevel()` 会把大于 4 的值夹到 4。
   结果：**"异动 → 补光降到 50%" 实际变成全亮**，"病蚕 → 补光 100%" 也是全亮，只有 `0` 有效。
   *修法*：P4 改成发档位（0~4），或 STM32 增加亮度百分比命令（推荐后者，配合调色一起做）。
2. **`/status` 是残桩** —— 返回 `camera=placeholder`、`sdcard=disabled`，均是写死的字符串，会误导排障。
3. **Kconfig 里几项已失效**：`CAMERA_FRAME_WIDTH/HEIGHT/RATE`（代码里硬编码 1080p/10fps）、
   `LOG_INTERVAL_SEC`（实际 5 s/10 s）、`VIDEO_KEEP_HOURS`（实际是 1 GB 水位）。
4. **`components/sensor_init/`** 是开发板例程残留，无任何引用，可删（删前跑一次 build 确认）。

## 8. 关键技术决策（为什么这么做）

写论文的「方案论证」章节直接可用。

### 8.1 MIPI-CSI 采不到图 → 码率配错

手写 CSI 初始化里 `lane_bit_rate_mbps = 200`，OV5647 实际是 **400 Mbps/lane**。
错误位恒为 `0x00`，极具误导性。改用官方 `esp_video`（V4L2 + ISP pipeline）后正常。

### 8.2 RAW8 在 IDF 6.1 被 CSI 桥白名单拒绝

`5.5.2` 放行 RAW8→RGB565，`6.1` 加了白名单 → `failed to configure format conversion`。
**不保证跨大版本兼容**，所以最终走 ISP 输出 RGB565，而不是自己转。

### 8.3 曝光不可调 → 自持 I2C 抢 AE 控制权

自动曝光在预编译库 `libesp_ipa.a` 里，没有可用参数。做法：直接用自建 I2C 写
`0x3503 = 0x03`（bit0 关 AEC、bit1 关 AGC），之后自己软件测光 + 直写曝光/增益寄存器。

### 8.4 降帧率换曝光时间（画质的关键一步）

VTS 决定单帧总行数，也决定曝光上限：

```
最长曝光 = (VTS − 4) × tline        tline ≈ 27.78 µs，fps ≈ 36000 / VTS
  1199 → 30 fps →  33 ms
  2400 → 15 fps →  67 ms
  3000 → 12 fps →  83 ms
  3600 → 10 fps → 100 ms   ← 当前
```

进光量 ×3（33→100 ms）→ 光子数 ×3 → **SNR ∝ √N → 噪声降约 1.7 倍（约 +4.6 dB）**。
而且 100 ms 恰好是 5 个 50 Hz 周期，**不会有工频闪烁**。
这是"降帧率不是性能妥协，而是成像质量优化"的完整论述。

### 8.5 SD 卡 `0x107` → 片内 LDO 通道 4

`sdmmc_init_ocr: send_op_cond (1) returned 0x107`。换了两套引脚都无效，
根因是 ESP32-P4 的 MicroSD 供电来自**片内 LDO 通道 4**，不 `sd_pwr_ctrl_new_on_chip_ldo()`
卡根本不上电。

### 8.6 断电后文件 0 字节 → 必须 `fsync`

`fflush` 只把数据交给 FATFS，**不更新目录项里的文件大小**。必须 `fsync(fileno(fp))`。
AVI 每 30 帧回填头部 + 索引；CSV 每行都 fsync（日志很小，代价可接受）。

### 8.7 AVI 头部的两个规范级错误（已修）

| 问题 | 后果 |
|---|---|
| `avih.flags = 0x10`（声称有索引）但断电文件没有 `idx1` | 严格播放器拒播 / 无法拖动 |
| `strh` 写 `scale=1, rate=7`，`avih` 写 `us/frame=127499` | 声明 7.00 fps，实际 7.84 → **时长报 3:00，实际 2:41（差 12%）** |

修法：flags 默认 0，`close()` 真写完 `idx1` 才置位；`strh` 用 `scale=us/帧, rate=1000000`。

### 8.8 UART 初始化顺序

必须 `param_config → set_pin → driver_install`。顺序颠倒会"能发不能收"。

### 8.9 推流会饿死 HTTP 服务

`/stream` 长连接占住 `esp_http_server` 唯一任务 → `ping` 通但 `/status` 超时。
改成 `httpd_req_async_handler_begin()` 把请求交给独立的流任务。
